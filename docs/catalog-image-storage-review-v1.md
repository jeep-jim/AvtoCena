# Хранение и доставка фотографий каталога

Проверено 07.09.2026; продолжение PR833. Обязательный контракт владельца: постоянные данные автомобиля и исходные URL фотографий — в JSON-чанках. Полный собственный фотоархив не создаётся.

## Вывод

Для выбранного продукта схема с URL обоснованна: объём постоянного хранилища не растёт на размер всех фотографий каждой машины. Ограниченный временный кэш по запросу совместим с этим подходом, но его наличие в production нужно подтверждать. Сам прокси не гарантирует снижение нагрузки или отсутствие блокировки: без кэша запросы посетителей концентрируются на IP прокси.

Общий кэш может повторно отдавать ответ многим посетителям; объединение одновременных запросов одного объекта уменьшает обращения к источнику при пустом кэше. Это описано в [MDN HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching) и [NGINX proxy_cache_lock](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_lock). Это техническое обоснование, не заявление, что такой NGINX сейчас развёрнут у АвтоЦены.

## Что подтверждено кодом и запросами

| Часть | Фактическое состояние |
|---|---|
| JSON | `runtime-config.ts` задаёт максимум 500 записей в чанке; галереи exact sources содержат исходные URL |
| Основная цепочка V3 | `CATALOG_IMAGE_STORAGE_MODE=source_urls_only` |
| Браузер | `CatalogCard` и `VehicleGallery` используют обычные `img`; карточки и миниатюры загружаются отложенно, основной открытый кадр — сразу |
| Внешние фотографии | `catalogImageDeliveryUrl` сохраняет source URL; один известный вариант Carused убирает уменьшение до миниатюры |
| Старые сохранённые изображения | `/api/catalog/images/[imageId]` читает существующий объект по индексу и выставляет `max-age=31536000, immutable`; это не прокси внешних URL |
| Два HEAD-запроса без тел фото | mobile.de CDN: HTTP 200, `max-age=2592000`, `X-Cache: Hit from cloudfront`; KCar: HTTP 200, `max-age=43200` |
| Автоматизация | В очереди V3 и workflow очистки сейчас нет cron: действует аварийная пауза |
| Срок хранения | Общий runtime и все найденные V2/V3/V4/recovery пути для неяпонских предложений приведены к 14 дням; временный staging и отдельный японский срок не менялись |

HEAD-проверка относится только к двум URL и не подтверждает все галереи. Существующая отсрочка при недоступности источника означает, что 14 дней не являются безусловным удалением каждой строки на следующий день. Оставшиеся трёхдневные значения относятся к временному staging, а не к сроку жизни предложений. План очереди — пять рынков раз в неделю; пока пауза активна, ранняя проверка останавливает очередь ещё до сетевого сбора. Cron не включён.

## Причина ошибки и исправление

В canary 40.77–40.79 был прямой вызов `cacheImageFromUrl`, обходивший URL-only wrappers. Сам loader не проверял режим, поэтому фотография скачивалась и сохранялась даже при выставленном `source_urls_only`. Я использовал этот путь для доказательства качества изображения, не соблюдая контракт хранения; необходимости менять архитектуру не было.

Исправление проверяет режим в самом loader. В `source_urls_only` и при отсутствии значения возвращается URL без image GET, чтения или записи файлового кэша. Неизвестное значение не включает скачивание. Старый бинарный путь требует отдельного явного режима `binary`; основной сбор его не включает. Добавленные этим PR преобразования JPEG/AVIF убраны.

Новый canary проверяет исходные URL, принадлежность свежей галерее, сохранение в JSON, публичную проекцию, расчёты и откат. Запись изображения блокируется. Единственное исключение из JSON-файлов — уже существующий сжатый текстовый CSV-фид `catalog/public/feeds/openai-products.csv.gz`; проверяется точный ключ, gzip и CSV-заголовок. Это не фотография, не загрузка источника и не фотоархив.

Визуальные замечания к рекламе и похожим кадрам остаются открытыми: ссылка сама по себе не доказывает качество содержания. Новый прокси автоматически не добавлялся; его необходимость следует определять по фактической доставке и нагрузке. Следующее условие для перезапуска — качество галерей, browser-приёмка и единый недельный регламент пяти рынков с исключённой Японией.

## Дополнительные исправления текущего прохода

В `auto-georgia-enriched-source.ts` найден второй прямой бинарный writer. Он теперь соблюдает тот же режим ссылок; уникальность изображений определяется по URL, если бинарного ID нет. Проверка реального адаптера с 30 адресами подтверждает отсутствие image fetch и обращений к файловому кэшу. Сам этот старый адаптер не входит в разрешённую production-очередь Грузии.

Подтверждено существование **серверных мостов сбора JSON** в `yandex-source-bridge.ts`. Encar и MyAuto ответили через них в проходе 34079770507; Guazi сообщил о source challenge. Это сбор описаний автомобилей сервером, а не проксирование посетительских фотографий. Штатные адреса и выбор маршрута в production не менялись. В диагностике первоначально слишком узкий сетевой допуск остановил эти пути до запроса; последующий проход разрешил только три точных GET-маршрута на одну страницу. Запросы upstream внутри уже развёрнутого сервиса отдельно не наблюдались.

`source-gallery-review-v1.json` содержит семь точных URL-исключений из предыдущего визуального просмотра: четыре рекламных изображения и три почти одинаковых вида приборов; две спорные галереи удерживаются до ручной проверки. Фильтр работает и при изменении размера того же изображения в query. Это небольшая очередь модерации, а не распознавание произвольных новых рекламных вставок. Новый архив фото не создавался; локальная browser-приёмка заблокирована политикой браузера этой сессии и не считается выполненной.
