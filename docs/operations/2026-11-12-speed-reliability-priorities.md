# 12.11.2026 — приоритеты скорости и надёжности

Статус: инженерные рекомендации и критерии выполнения, а не утверждение об уже установленной системе. Продолжение разрешённой владельцем работы. Цены, права поставщиков, ручные данные и существующие пороги приёмки сохраняются.

## Подтверждённая отправная точка

- Компактные индексы локальных рынков уже существуют. Не создавать второй каталог без сравнения с существующим путём.
- JP/KR фильтруют мощность после получения ограниченных порций. Полный локальный индекс зависит от разрешённых поставщиком данных и подтверждённого покрытия мощности.
- Существуют cooldown поставщика, ограниченные очереди и защита выпуска. Требуется проверка фактического охвата, а не повторная реализация под другим названием.
- PR1756 принят в main. Изолированный PR1757/04f2fa19 на базе a182 получил 2853 успешных теста и один отказ старой фикстуры: projectionModelKeys не передана в new Function. Исправление этой фикстуры уже есть в main; переносится отдельно без изменения поиска. Новая версия не установлена.
- Проверка сервера 43152914278: блог 0.1698/0.8137/0.0707 с, без CPU throttling в шести окнах. Это не браузерное время и не доказательство причины исторических зависаний.

## Последовательность

1. Закончить минимальный выпуск PR1757: исправить зависимость тестовой фикстуры, получить exact-source CI, подготовить контроллер с прежними неизменными серверными/браузерными воротами и откатом. Не устанавливать весь main.
2. Для каждого рынка проверить, что обычные фильтры, счётчики и доступные значения читаются из одного готового поколения. Карточки ограничивать на сервере до требуемого дизайном размера. Не отдавать весь рынок браузеру и не фильтровать только первые шесть машин. Счётчик считать по всему подходящему набору; количество карточек не равно количеству совпадений.
3. Обновлять поколения отдельно от посетительских запросов: собрать, обогатить, проверить, подготовить индекс/цены, затем переключить указатель. Ошибка обновления не удаляет принятую базу; актуальность, отзыв объявлений и ценовой контекст остаются проверяемыми. При просрочке не выдавать старые цены за свежие.
4. Изолировать фоновые задачи и рынки: ограничение CPU/памяти/очередей сборщиков и тяжёлых преобразований, самостоятельные сроки ожидания рынков. Один отказ не должен блокировать блог и остальные рынки. Проверять existing cooldown, объединение одинаковых запросов и отмену устаревших запросов без смешения visitor IP/прав/города.
5. Измерять путь от клика до правильных карточек и отдельно этапы серверного ответа: очередь, источник, хранилище, обогащение, расчёт, сериализация. Агрегировать по рынку/типу фильтра/версии; без персональных параметров и токенов. Отдельно p50/p95, ошибки, неполные выдачи, возраст индекса. Первичная цель для локального поиска — p95 до 1 с при согласованной нагрузке; это новая цель, не замена старых строгих эталонов.
6. Снизить работу браузера: только нужные размеры изображений; первый экран без принудительной ленивой задержки; остальные фотографии при приближении. Загружать галереи, отчёты и чат по действию. Измерить JS, длинные задачи, LCP/INP/CLS и SVG/анимации. Удалять только подтверждённо дорогие элементы; формат SVG сам по себе не диагноз.
7. Подготовить кэшируемый публичный блог с корректным обновлением при редактировании/снятии публикации. Персональные и CRM ответы не помещать в общий кэш. Проверить HTTP cache policy для статичных версионированных ресурсов. CDN рассматривать после измерения пути из РФ и прав на фото; покупка не выполняется.
8. Расширить приёмку на все рынки, мощности <=160, комбинации фильтров, пагинацию, город, пустой результат, отказ поставщика, истечение кэша и нагрузку. Проверять полный состав/цены и число запросов, а не быстрый HTTP200. Проверить восстановление резервной копии в отдельной среде. Резервный узел и переключение трафика проектировать после согласования требований доступности и расходов; один сервер не считать защитой от отказа узла.

## Выбор поискового хранилища

Сначала измерить готовые существующие индексы и их запас под целевой нагрузкой. Если при полном покрытии фильтров/счётчиков и корректных индексах они не выполняют требования, провести отдельный обратимый прототип PostgreSQL с индексами по фактическим запросам. Сравнить с текущим путём на одинаковом наборе данных и нагрузке: p95, полнота, обновление, потребление памяти/диска. Redis и отдельный поисковый движок не вводить пакетом без доказанной задачи. Производственная миграция этим документом не выполнена.

## Порядок выдачи

Для разнообразия допустим устойчивый порядок на время просмотра. Новый случайный порядок на каждой странице не использовать: переходы должны исключать дубли и пропуски. Сортировка по цене/году имеет приоритет над разнообразием. Курсор должен сохранять фильтры, город, версию данных и порядок; смену поколения обрабатывать явно.
