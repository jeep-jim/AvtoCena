Mapper исправляется отдельно. Для разрешения запуска source SHA должен содержать проверенный mapper, в том числе последующие исправления проверки неоднозначных полей и неподтверждённой 30-минутной мощности. Этот workflow не устанавливает приложение, не переключает источники и не меняет расписание.

## Почему полный повтор старого intake не подходит

Обычный платный intake считается полным активным набором. В `catalog-publish-market.mjs` такой report исключает retained Korea rows. Если передать старый снимок целиком, он может заменить актуальные цены и вернуть ID, которых уже нет в опубликованном наборе. Отдельного запрета исправлений при одинаковом `observedAt` в этом пути нет; менять дату наблюдения ради ремонта не требуется.

Ремонт строит вход из **текущих** объявлений. Старый снимок используется только для их пересечения по стабильному ID и исходному Encar ID. Исторические дополнительные ID не попадают во вход. Текущие source price/currency, статус, фотографии, даты наблюдения, source identity и ручные данные сохраняются. Расчётные итоги разрешено пересчитать; исходная цена продавца от этого не меняется.

Обновлённая позже запись, другой исходный год, отсутствующий пригодный исторический источник или конфликт технических полей остаются без такой коррекции. Проверенные внешние технические сведения сохраняются. Маркеры `manual`/`customer_input`, `manualEditedAt` и `calculationSnapshot.modificationScenario` защищают всю запись от технического переноса, включая отдельную смену привода. Полный персональный calculation snapshot входит в контрольный хеш ручных данных.

Результат перечисляет фактические причины пропуска. Он не утверждает, что все поля всех автомобилей исправлены, если ограничения не позволили их изменить.

## Проверки публикации

`paid-encar-technical-repair.mjs` строит детерминированный receipt. Он связывает exact source/controller SHA, actual serving release/calculator, текущее поколение и ETag manifest, UTC-день и день политики UTC+7, снимок и хеши его страниц. Отдельно закрепляются ETag и содержимое CRM editorial, collection controls и Korea intake cursor.

| Контроль | Что должно совпасть |
| --- | --- |
| Исходный набор | Полный хеш текущих строк, количество и точный набор ID |
| Вход publisher | Полный хеш сформированных исправленных строк |
| После canonical preview | ID, source price/currency, freshness, media, manual и другие сохраняемые атрибуты |
| Под import lease | Manifest, protected objects, health, даты и владелец действующей блокировки |
| Перед generation writes | Те же инварианты нормализованных и канонических строк |
| После staged price preparation, до aliases | Повтор exact repair authority рядом с raw provenance verification |
| Перед manifest CAS | Repair authority, исходная CAS/lease-защита, raw provenance и fresh serving-runtime readiness |
| После CAS | Новое прямое чтение всех Korea chunks и проверка receipt; отдельные счётчики изменений расчётных цен |

Публикация использует обычные quality/count/retention gates и штатный `prepareStagedCatalogBudget` с реальной установленной версией калькулятора. Чужие рынки сохраняются штатными полными хешами. Если обычная очистка собирается удалить даже запрещённый старый хвост другого рынка, этот узкий ремонт останавливается: такая очистка не входит в его scope.

Неизвестная или некорректная дата lease не считается свободной блокировкой. Любая смена protected object, поколения, health identity или дня требует нового plan. Корея не объявляется опубликованной и проверенной, если свежий readback не прошёл. Если ошибка обнаружена после реального manifest CAS, report честно содержит опубликованное поколение и `technicalRepair.verified=false`; job завершается ошибкой, raw pin не освобождается. Автоматического отката через чужую последующую публикацию нет.

## Два ручных действия одного controller

В поставляемом файле `.github/workflows/repair-paid-encar-technical.yml` job отключён, source pin — `UNASSIGNED`. После CI и review нужно одним controller commit назначить точный source SHA и включить этот ручной job. **Plan и apply используют один и тот же controller commit.** Иначе controller SHA в receipt закономерно изменится. Значение по умолчанию — `plan`; автоматического apply нет.

1. После согласования с действующим writer выполнить `plan` с точными release/calculator из health. Он проверяет отсутствие import lease, читает только сохранённые объекты, строит receipt и запускает **dry-run штатного publisher**. Сетевой guard запрещает S3 PUT и запросы поставщиков. Результаты: `summary.json` и `publication.json` с фактической canonical coverage; успешное построение входа само по себе ещё не означает успешный plan.
2. Проверить успешный job, source identity, текущий размер набора, причины пропусков, сохранённые хеши и canonical proof. Назначить `approved_plan_sha256` из этого результата. После принятия нового app release, смены дня или CRM/manifest требуется новый plan; старый результат не переименовывается под новый runtime.
3. Явно выполнить `apply` того же controller с approved receipt. Он заново читает текущий набор и снимок, воспроизводит receipt и сравнивает его полностью. Совпадение подтверждается до generation writes, затем повторно под обычной publication lease.
4. Проверить `technicalRepair.verified=true`, before/after хеши, derived-price change counts, новое поколение, staged readiness и raw pin handoff. Intake cursor не продвигается, потому что новых supplier observations нет.

Apply использует общую concurrency `production-release`. Read-only plan имеет собственную concurrency; если manifest/health меняются во время его чтений, authority gate останавливает результат. Обычные market writers дополнительно сериализуются действующей import lease.

## Хранение и сетевые границы

Plan не создаёт raw pins и ничего не пишет в Object Storage. Apply до чтения raw источника открывает loading pin с **новым фактическим** workflow run/attempt/controller; это только защищающие метаданные. После чтения и проверки approved receipt он передаёт ready handoff обычному publisher. Все исходные observation/report roots текущих записей сохраняются; старый producer SHA не подставляется в owner нового pin. При отказе защитный pin остаётся для последующего owner-aware cleanup.

Внешняя сеть ограничена назначенным Object Storage, `/api/health` и официальным CBR rate endpoint. Сохранённый источник, reports, CRM, controls и cursor запрещены для записи; удаления запрещены полностью. Существующая проверка свободного места может читать список метаданных назначенного bucket. Workflow не получает supplier key. Исходные страницы, готовые входные объявления и полный receipt не публикуются как Actions artifacts; сохраняются только summary, publication proof и staged readiness report.

## Проверенные ограничения

Офлайн tests проводят исправленные Morning/Seltos через настоящий `prepareSellerInventory`, compact storage и public projection, а не только сравнивают mapper output. Они проверяют новые/потерянные ID, цены, даты, медиа, ручные свойства, подмену исходника, metadata bounds, malformed lease, authority drift и network fence.

Отдельные реальные пути подтверждают два условия отказа. Обычный seller pipeline может заменить сохранённый персональный scenario; repair guard в этом случае блокирует plan до записи. Старый retained trim может снова породить неподтверждённую 30-минутную мощность при повторной нормализации; receipt проверяет отсутствие такой новой мощности и производного utilization у гибрида/EV. Этот ремонт не ослабляет проверки, чтобы скрыть такие случаи. Их наличие в реальном наборе станет видимым результатом plan и потребует отдельного решения до apply.

Ни запуск этого workflow, ни исправление рабочего каталога этим документом не подтверждаются.
