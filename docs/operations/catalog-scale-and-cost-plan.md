# АвтоЦена: оптимизация каталога в Yandex Cloud

Дата: 10.10.2026, Asia/Krasnoyarsk. Статус: согласованное направление владельца; первый этап реализуется. Это план, а не заявление о достигнутом снижении расходов.

## Границы

- Остаёмся в Yandex Cloud. Ресурсы production не уменьшаются вслепую.
- Основная база фидов едина для всех дилеров. Не создаём копию инвентаря на каждого дилера.
- Объявления дилеров в разделах «Под заказ» и «Б/у», их медиа, кабинеты, документы, заявки и персональные данные сохраняются в Яндексе. Не отправляем их в публичные GitHub repositories, logs, artifacts или Actions cache.
- Купленная база поставщика также не публикуется в Git без отдельного права на распространение. Видимость отдельных карточек сайта не означает право раздать исходную выгрузку целиком.
- Допуск, идентичность, подтверждённое снятие, русский интерфейс, неизвестные характеристики, все рынки и отдельные правила Японии сохраняются. Ошибка подготовки не означает продажу или удаление машины.

## Репозитории и исполнение

Рекомендуемая целевая схема: основной приватный репозиторий с приложением, общим движком, адаптерами и автоматизацией. Второй публичный репозиторий необязателен; в него допустимо выделять только сознательно открываемые универсальные инструменты, искусственные примеры и документацию. Ни коммерческие правила, ни производственные выгрузки, ни доступ к CRM ему не нужны.

Публичный репозиторий не является закрытым кешем, базой данных или постоянно работающим backend. Выполнение приватного кода из публичного workflow требует отдельного контроля логов, artifacts, токенов и событий запуска; такую схему не выбираем только ради бесплатных минут. GitHub bills reusable workflows по вызывающему workflow, а не по месту хранения вызываемого файла.

Перед переводом AvtoCena в private: проверить доступ установленного GitHub App к private repository, authenticated checkout, Actions quotas/budget, внешние raw/download ссылки, сборку Docker и доставку образа. Проверить один штатный deploy и фид после смены видимости. В этой сессии видимость не изменена; в доступном GitHub connector нет операции изменения настроек репозитория. Наличие admin в GET permissions не добавляет эту операцию инструменту.

Private ограничивает будущий доступ через GitHub, но не отзывает уже скачанный код; публичные форки при закрытии не становятся приватными. Клиентский JavaScript, отправленный браузеру, остаётся доступен пользователю сайта. Серверные секреты и правила должны оставаться на сервере.

Источники условий GitHub, проверены 10.10.2026:
- https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility
- https://docs.github.com/en/actions/concepts/billing-and-usage

## Расчёты и дилеры

1. Общие исходные сведения об автомобиле и доказательства характеристик.
2. Единый версионируемый расчёт обязательных платежей: таможня, утиль, применимые правила и официальные курсы. Настройки дилера не изменяют этот слой.
3. Отдельная версия разрешённых коммерческих настроек дилера: услуги, комиссия, логистика и другие разрешённые поля. Явная схема полей исключает изменение закона или общего курса под видом услуги.
4. Город доставки и пользовательский сценарий. Ручная модификация влияет только на свой сценарий, не на глобальную машину.

Ключ результатов включает generation каталога, версию движка/правил, используемые курсы, значимую дату, версию коммерческих настроек и идентификатор дилера; при необходимости город и параметры сценария. Нельзя кешировать только по offerId. Нельзя смешивать кеш авторизованного кабинета с общедоступной выдачей.

Если стоимость дилерских услуг влияет на попадание в бюджет или сортировку, её учитывает поисковый запрос до пагинации. Пересчёт только 12 уже выбранных карточек в таком случае неверен. Для поддерживаемых формул используем индексируемые компоненты цены и преобразование бюджетной границы; для остальных — отдельный производный ценовой индекс по версии настроек, без копирования всего инвентаря. Сложные формулы требуют доказанного совпадения с основным движком.

## Этапы и критерии

| Этап | Работа | Проверка результата |
|---|---|---|
| 1 | Суточное обновление первых страниц рынков и сводки главной на GitHub | Тот же порядок и количество; ни одного чтения полной проекции для поддерживаемой первой страницы; проверки даты, поколения и конкурирующей записи |
| 2 | Возобновление подготовки цен после занятой блокировки; явные ready/skipped/failed, повтор и сигнал просрочки | Готовые результаты именно для production SHA, generation, курса и настроек; зелёный workflow не заменяет verified=true |
| 3 | Уменьшение selector: фильтры и сортировка по компактным индексам, чтение только блоков найденных карточек | Паритет всех рынков, бюджетов/городов, фильтров, сортировок, пропусков данных и редакторских скрытий; bytes/read, CPU, p50/p95 |
| 4 | Версионирование коммерческого слоя дилеров и изоляция кабинетов | Изменение одного дилера не меняет другого; общий движок неизменен; поиск по бюджету совпадает с карточкой |
| 5 | Сравнение Serverless и постоянной VM внутри Яндекса на одинаковой версии/нагрузке | Полная стоимость CPU/RAM, трафика, диска, резервирования; ошибки и p95 под одновременными запросами |
| 6 | Постепенный выпуск, наблюдение за полными сутками и откат | Оплаченные ресурсы и стоимость на 1000 запросов сопоставлены с одинаковой нагрузкой, а не только один быстрый ответ |

GitHub готовит обновления, но работа сайта между публикациями не должна требовать доступности GitHub. В Яндексе хранится проверенное опубликованное поколение и предыдущее для отката. Не переключаем указатель до проверки всех необходимых производных данных. Старые цены нельзя бесконтрольно выдавать как актуальные при смене курса/правил; до завершения обновления сохраняется точный действующий путь.

Сотни тысяч пользователей в месяц недостаточны для расчёта мощности. Нужны peak requests/sec, число запросов на посещение, доля поиска/фото/кабинетов, одновременность и cache hit. Цели нагрузочного теста задаём по этим значениям. Сам тест сначала на копии, а не массовым трафиком в production.

## Первый выпуск: границы

Суточный builder обновляет date-sensitive market landing через ETag, затем overview; почасовая резервная проверка пропускает тяжёлую работу, когда текущее поколение/день уже подготовлены. При занятом publisher задача завершается ошибкой и следующая плановая проверка повторяет попытку. GitHub schedule может задерживаться: мгновенного обновления в полночь эта мера не гарантирует.

Этот этап не устраняет тяжёлые фильтрованные запросы, смену даты до завершения builder, дорогой путь при редакторских скрытиях и полный пересчёт при промахе ценового кеша. Они остаются явными следующими задачами; процент экономии до биллинга не объявляется.
