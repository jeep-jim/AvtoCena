# Проверка хранения японского кэша

Этот controller-путь готовит доказательства для безопасной очистки AJ-кэша. Он не выпускает приложение, не меняет настройки bucket и не удаляет рабочие объекты кэша. Его публикация сама по себе не означает, что аудит или синтетическая проверка уже выполнены.

## Два отдельных режима

| Workflow | Режим | Допустимые действия |
| --- | --- | --- |
| `japan-cache-retention-audit.yml` | `--audit` | Чтение versioning/lifecycle, ограниченный просмотр метаданных заданных AJ-префиксов и не более восьми просроченных ответов в памяти для проверки возраста. |
| `japan-cache-retention-canary.yml` | `--canary` | Проверка условных операций на одном новом непредсказуемом ключе, принадлежащем этому запуску и расположенном вне рабочего AJ-кэша. |

В режимах нет запросов к поставщику AJ, обхода его каталога, подмены IP или полного сохранения ответов в artifacts. Canary не превращает неподдерживаемое условное удаление в обычное удаление. Если неверный ETag не сохраняет обновлённый тестовый объект, возможность считается неподтверждённой. Для versioned bucket удаление синтетических остатков ограничено известными непустыми `VersionId`; если безопасное завершение не подтверждено, отчёт явно сообщает о небольшом тестовом остатке.

Эта проба проверяет только заголовок DELETE `If-Match` со значением ETag в кавычках: отчёт явно указывает `conditionalHeaderFormat: "quoted"` и тип проверяемого объекта. Отказ такого запроса не доказывает отсутствие поддержки другого формата, в том числе значения без кавычек, используемого существующим REG transport для условного PUT. Для проверки другого формата понадобится отдельная согласованная проба на новом собственном canary; автоматического перехода на другой формат или безусловное удаление здесь нет.

Текущие объекты, неактуальные версии bucket и диск сервера учитываются отдельно. Маленькая новая версия объекта не доказывает физическое освобождение старой версии. Отсутствие lifecycle или неподтверждённая возможность удаления не даёт разрешения на очистку рабочего AJ-кэша.

## Жёсткие пределы проверки

| Область | Предел |
| --- | --- |
| AJ-префиксы | Только `catalog/partner-cache/ajes/stats/`, `main/` и `queries/` в закреплённом staging prefix. |
| Метаданные | Не более двух страниц по 100 ключей на каждый из трёх префиксов; неполный обход явно отмечается. История версий не перечисляется. |
| Тела старых объектов | Не более восьми объектов с возрастом метаданных не меньше семи дней. GET связан с ETag из LIST; изменение объекта означает пропуск. |
| Размер чтения | До 2 MiB для одного detail, до 256 KiB для query или XML; до 20 MiB ответа суммарно. Тело используется только в памяти. |
| Запросы и время | До 32 запросов, до 8 секунд на запрос и до 120 секунд на операцию, без повторов. |
| Синтетическая запись | Один run-owned ключ с 192-битным случайным суффиксом, не более двух PUT по 512 байт. При непроверенном удалении возможный остаток явно отражается в отчёте. |
| Итоговый файл | Не более 32 KiB, только агрегаты, безопасные коды результата и идентификатор собственного canary. |

Возраст `LastModified` нужен только для отбора восьми кандидатов. Внутри каждого такого объекта отдельно проверяется исходный `observedAt`: свежая запись не объявляется просроченной из-за возраста другого сохранённого ответа. Выводы ограничены просмотренными текущими объектами и не являются полным подсчётом объёма AJ или диска сервера.

## Проверка исходника перед запуском

Сначала пройти review и offline tests, затем опубликовать проверенный controller-код в `main`. Root запускает проверку после завершения активного японского выпуска и подтверждения его конечного состояния. Режимы не зависят от принятия нового runtime: рабочий AJ-кэш не изменяется. Расписания для этих workflow нет; автоматическая очистка ими не включается.

Для ручного `workflow_dispatch` выбрать нужный workflow на `main` и передать его полный проверенный SHA в `expected_controller_sha`. Значение должно в точности совпадать с `GITHUB_SHA` и checkout `HEAD`. Оно передаётся через переменную окружения, без подстановки во фрагмент shell.

Альтернативный запуск использует отдельный marker-only commit, чей единственный родитель — уже опубликованный и проверенный tip `main`. Такой commit изменяет ровно один соответствующий marker-файл:

| Режим | Marker | `operation` |
| --- | --- | --- |
| Audit | `.github/market-runs/japan-cache-retention-audit.json` | `japan-cache-retention-audit-v1` |
| Canary | `.github/market-runs/japan-cache-retention-canary.json` | `japan-cache-retention-canary-v1` |

Шаблон для audit; заполнитель нужно заменить полным SHA уже проверенного родителя. Это пример документации, а не готовый marker:

```json
{
  "version": 1,
  "operation": "japan-cache-retention-audit-v1",
  "approvedSourceSha": "<REVIEWED_CONTROLLER_SHA>"
}
```

Для canary используется отдельный marker и `operation` из таблицы. Проверка отклоняет изменение controller-кода вместе с marker, неправильный SHA, чужой репозиторий, другую ветку, другой workflow или job, force push и повторную попытку GitHub job. Публикация исходников workflow не запускает проверку: push-триггеры следят только за указанными marker-файлами. Оба workflow используют одну группу concurrency с `cancel-in-progress: false`.

До доступа к storage credentials workflow проверяет исходные speed-baseline hashes, точную команду запуска и offline fence tests. Npm-установка и пересборка runtime не нужны.

```bash
node scripts/verify-frozen-speed-baselines.mjs
node --import ./tests/helpers/offline-fetch.mjs --test --test-concurrency=1 tests/catalog-next-japan-cache-retention.test.mjs tests/catalog-next-japan-cache-retention-workflow.test.mjs tests/readonly-marker-invocation.test.mjs
```

## Отчёты и дальнейшая очистка

Единственные публикуемые файлы — `japan-cache-retention-audit-report.json` или `japan-cache-retention-canary-report.json`, срок хранения artifact — 14 дней. В них допускаются только санитизированные итоги и ограниченные коды результата; тела ответов, credentials, SQL, visitor IP и коммерческие данные не публикуются.

Отчёт является подготовкой к следующему решению: какой безопасный механизм очистки поддерживает фактический backend и что останется в истории версий. Реальное удаление AJ cache требует отдельного проверенного executor, защищающего свежую запись от гонки с работающим runtime. В этом пути такого executor нет.
