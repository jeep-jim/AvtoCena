Эти ограничения объясняют конкретные риски очередей/неполноты, но не устанавливают единственную причину каждого отказа.

## Выпуск кода и обслуживание посетителей — разные цепочки
.github/workflows/regcloud-deploy.yml собирает Docker-образ на runner, сохраняет/проверяет SHA256, передаёт образ по SSH/SCP на REG-сервер и загружает Docker. Dockerfile запускает node apps/web/server.js из standalone-сборки. Рабочие страницы обслуживаются nginx/Node на REG с данными из настроенного object storage, локальных кешей и разрешённых API; GitHub не является промежуточным сервером выдачи каталога.
В исходниках найдены отдельные GitHub-интеграции crm-dispatch.ts и team-assistant/repository.ts. Поэтому утверждение «всё приложение вообще не зависит от GitHub» было бы слишком сильным. Они не являются передачей каждого каталожного запроса через GitHub.
Отказ от GitHub сам по себе не уменьшит HTML, не исправит provider refusal, не создаст точный индекс мощности и не ускорит те же запросы на том же сервере. Разработка на рабочем сервере без истории/проверок увеличит риск неповторимых изменений; сборки на том же CPU могут конкурировать с посетителями. Возможная отдельная задача — ускорить подготовку релиза и переиспользование неизменных индексов, сохраняя версионность, проверки и откат. В этой сессии выпуск/источники/права/цены не изменяются.
