## Подтверждено по коду

- Dockerfile уже собирает Next standalone на Node 22, включает ffmpeg, слушает порт 3000.
- `.github/workflows/deploy-yandex.yml` привязан к `cr.yandex` и Serverless Containers.
  Для нового сервера нужна отдельная выкладка, не повтор старого workflow.
- `apps/web/lib/data.ts` принимает S3 endpoint/region/bucket/credentials/prefix через
  `YC_OBJECT_STORAGE_*`. Названия переменных можно сохранить; значения задавать отдельно.
  Endpoint/region нельзя оставлять пустыми: имеются значения по умолчанию для Яндекса.
- Запись JSON и binary использует If-Match / If-None-Match и ожидает 409/412 при конфликте.
  Проверить эти операции на новом S3 до переноса клиентских записей.
- По поиску 107 файлов workflow упоминают YC_OBJECT_STORAGE; это не 107 активных задач.
  Нельзя глобально менять секреты перед проверкой всех реально активных писателей.
- `apps/web/lib/account/mail.ts`: Postbox получает токен через metadata Яндекса.
  При переносе на другую VM этот путь не переносится автоматически. Уже есть SMTP-путь;
  для него нужны подтверждённые SMTP-настройки и проверка доставки.
- SmartCaptcha, Telegram, YooKassa, CRM GitHub dispatch и сборщики требуют отдельной проверки.
  Китайский фид сохраняется, HTML-парсеры Китая и автоматические recovery не включаются.

## Порядок работ

1. Подтвердить доступ к GitHub с правом записи и Actions, а также к REG Cloud, S3 и SSH.
   Не считать доступ к публичному git remote подтверждением права записи.
2. Создать один тестовый сервер и изолированное хранилище. Первоначально приложение
   доступно только через SSH-туннель (bind 127.0.0.1:3000), без публичного доступа к копии CRM.
   Отдельные тестовые AUTH_SECRET/AUTH_ACCESS_KEY, без боевых отправок, платежей и dispatch.
3. Сборка на стандартном GitHub-hosted runner из того же репозитория. Передача образа
   на VM по SSH с проверенным host key; не зависеть от реестра Яндекса. Отдельный
   manual-only workflow и отдельные секреты окружения; workflow ещё не реализован.
4. Проверить S3 на синтетических объектах: conditional PUT, conflict, HEAD, list pagination,
   binary upload/download, подписанные ссылки, приватность документов. Не удалять боевые объекты.
5. Скопировать данные из Яндекса с сохранением ключей/метаданных в изолированную цель.
   Проверить количество, размеры и контрольные суммы; multipart ETag не считать MD5.
   Во время недоступности источника нельзя обещать полноту копии.
6. Проверить каталог всех рынков, цены/курсы/доставку, фильтры, картинки, CRM, вход,
   клиентский чат и документы. Отдельно проверить SMTP и уведомления тестовым получателям.
   Нагрузку проверять ограниченным согласованным прогоном, без периодического watchdog.
7. Перед переключением остановить все старые писатели (включая сборщики и фоновые доставки),
   завершить текущие записи, сделать финальную синхронизацию и сверку. После переключения
   включить только одну группу писателей. Не допускать параллельной записи в две разные базы.
8. Переключить фактически обслуживающий DNS, проверить TLS, webhooks и точный release SHA.
   Расположение регистрации домена не доказывает, что DNS обслуживает REG.RU.
9. Откат после новых заявок требует обратной синхронизации данных; одного возврата DNS мало.
   Старые ресурсы выключать после проверки, чтобы остановить двойную оплату.

## Подготовленная проверка

изолированного стенда, не обращается в сеть и не печатает ключи. Она не проверяет права
самих S3-ключей: нужны отдельный бакет/ограниченные ключи. Успех не доказывает готовность сайта.
