## Порядок работ

1. Подтвердить доступ к GitHub с правом записи и Actions, а также к REG Cloud, S3 и SSH.
   Не считать доступ к публичному git remote подтверждением права записи.
2. Создать один тестовый сервер и изолированное хранилище. Первоначально приложение
   доступно только через SSH-туннель (bind 127.0.0.1:3000), без публичного доступа к копии CRM.
   Отдельные тестовые AUTH_SECRET/AUTH_ACCESS_KEY, без боевых отправок, платежей и dispatch.
3. Сборка на стандартном GitHub-hosted runner из того же репозитория. Передача образа
   на VM по SSH с проверенным host key; не зависеть от реестра Яндекса. Отдельный
   manual-only workflow и отдельные секреты окружения; workflow ещё не реализован.
4. Проверить S3 на синтетических объектах: conditional PUT, conflict, HEAD, list pagination,
   binary upload/download, подписанные ссылки, приватность документов. Не удалять боевые объекты.
5. Скопировать данные из Яндекса с сохранением ключей/метаданных в изолированную цель.
   Проверить количество, размеры и контрольные суммы; multipart ETag не считать MD5.
   Во время недоступности источника нельзя обещать полноту копии.
6. Проверить каталог всех рынков, цены/курсы/доставку, фильтры, картинки, CRM, вход,
   клиентский чат и документы. Отдельно проверить SMTP и уведомления тестовым получателям.
   Нагрузку проверять ограниченным согласованным прогоном, без периодического watchdog.
7. Перед переключением остановить все старые писатели (включая сборщики и фоновые доставки),
   завершить текущие записи, сделать финальную синхронизацию и сверку. После переключения
   включить только одну группу писателей. Не допускать параллельной записи в две разные базы.
8. Переключить фактически обслуживающий DNS, проверить TLS, webhooks и точный release SHA.
   Расположение регистрации домена не доказывает, что DNS обслуживает REG.RU.
9. Откат после новых заявок требует обратной синхронизации данных; одного возврата DNS мало.
   Старые ресурсы выключать после проверки, чтобы остановить двойную оплату.

## Первичная копия — 11.10.2026

- Подтверждён лимит REG 100 ГБ; исходные текущие объекты: 35226 / 56191425937 байт.
- Ручной workflow regcloud-copy-data.yml передаёт данные через уже созданный REG-сервер. GitHub не хранит содержимое объектов в артефактах/логах. Конфигурация доступа передаётся по SSH с закреплённым host key и хранится в root-only временном файле, удаляемом при выходе.
- Цель фиксирована: avtocena-staging-8120751 / migration-staging/full-20261011/. Производственный сайт пока не должен использовать этот префикс. Три потока, временный файл на объект, максимум 2 ГБ на объект, таймаут 165 минут на сервере.
- Чтение исходника условное по ETag. Копирование сохраняет Content-Type, Cache-Control, Content-Disposition, Content-Encoding, Content-Language, Expires и пользовательские метаданные; добавляет контрольную сумму и отметки исходной версии. Каждая новая запись перечитывается из REG и сравнивается по SHA-256. Возобновление использует ETag/LastModified/размер источника и повторно проверяет SHA-256 цели.
- Исходник и цель не очищаются. Если источник изменился или в копии есть лишние объекты, запуск не объявляет согласованность. Для финального переключения нужны остановленные писатели, повторная синхронизация и отдельное разрешение ситуации с удалёнными объектами. Исторические версии и multipart не переносятся этим шагом.
- До первого использования копии рабочим сайтом обязательно создать на VM /opt/avtocena/PRODUCTION_ACTIVE: это блокирует повтор начального копирования поверх рабочего префикса. Отдельно нужны резервирование, SMTP, вебхуки, проверка сайта и DNS.
- Частичная копия при ошибке сохраняется; продолжение возможно ручным новым запуском. Из-за полной контрольной проверки продолжающий запуск повторно читает уже скопированные данные REG.

## Сверка после конфликта очистки — 11.10.2026

`regcloud-copy-data.yml` перед переносом приостанавливает GitHub workflow, использующие старые S3/YC credentials, и их вызывающие workflow. Прежние состояния сохраняются как `regcloud-paused-workflows-<run>-<attempt>`. Возвращать только ранее активные задания после проверки их нового места записи; не включать всё подряд. Внешние приложения/таймеры этим не остановлены. При изменении источника проверка остаётся красной.

Режим REGCLOUD_RECONCILE=1 сохраняет лишние staging-объекты в `migration-staging/quarantine-20261011/` внутри REG, проверяет содержимое и заголовки, записывает fsync recovery mapping в `/opt/avtocena/staging/migration/quarantine-recovery.jsonl`, затем удаляет только исходный staging-ключ. Quarantine остаётся для восстановления; автоматически её не очищать. Источник Яндекса не изменяется. Проверка полного текущего объёма остаётся обязательной, поэтому повторный прогон не мгновенный. Готовность DNS по-прежнему false.
