# CRM → Яндекс Метрика (счётчик 112098062)

Подключение: `/crm/settings/metrika`, только владелец/администратор. OAuth-токен с правом `metrika:write` вводится в защищённой форме. Проверяется доступ к заданному счётчику, читается его часовой пояс и создаются недостающие JavaScript-цели с точным совпадением идентификаторов. Токен шифруется AES-256-GCM ключом, производным от серверного AUTH_SECRET; в браузер/логи не возвращается. Смена AUTH_SECRET требует повторного подключения.

| Действие | Цель |
| --- | --- |
| Успешная заявка на сайте | `lead_submitted` — Заявка отправлена |
| Статус «Квалифицированный лид» | `crm_qualified` — Квалифицированный лид |
| «Договор подписан» либо «Оплата получена» | `crm_contract` — Договор / оплата |
| Явный статус «Спам» с причиной | `crm_spam` — Спам |

Нет ответа и отказ не становятся спамом автоматически. При оплате передаётся PAID; подписанный, но неоплаченный договор остаётся IN_PROGRESS с дополнительной целью. Сумма автомобиля/бюджет не выдаётся за реальную выручку.

Общие формы сохраняют ClientID Метрики и yclid вместе с заявкой. Экспорт использует ClientID; без него заявки пропускаются и отражаются в счётчике диагностики. Телефоны, имена, сообщения и OAuth-токен не включаются в файл заказов.

Фоновый job `metrika` в `crm-telegram-delivery.yml` запускается по существующему расписанию (раз в 5 минут, фактическое время зависит от GitHub) и после деплоя. Использует CRM object storage и AUTH_SECRET из существующих secrets. Список заказов экспортируется через simple_orders, merge_mode=SAVE, по стабильному ID заявки. Хеш отправленной версии предотвращает повторную загрузку неизменённых данных. При HTTP/validation-ошибке версия не отмечается принятой и будет повторена. История квалификации/договора сохраняется в дополнительных целях, даже если менеджер сменил несколько статусов между проходами. Для текущего статуса «Спам» положительные цели не экспортируются.

Первая отправка ограничена заявками последних 21 суток, обновления ранее принятых — 111 сутками от создания заявки. Это консервативный технический фильтр; действительное сопоставление с визитом проверяет Яндекс. Архивные заявки не экспортируются. Приём API PASSED не является подтверждением привязки/достижения цели в отчётах; lastUploadId и время приёма доступны в админке. Менеджеру рекламы нужно выбрать цели для оптимизации и настроить исключение спам-сегмента в Директе отдельно.

Проверка: `node --import tsx --test tests/metrika-crm.test.ts` (данные/время, статусы, отсутствие выдуманной выручки, шифрование, настройка целей, отказ API, повторная попытка, дедупликация). Для проверки боевого сопоставления после подключения нужна настоящая заявка из отслеживаемого визита; тестовые сделки в рабочую Метрику автоматически не отправляются.
