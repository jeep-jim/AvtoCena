# Фотографии, защита и мобильная CRM — 21.09.2026

## Область проверки

Проверены текущий код, зависимости, ограниченная выборка публичного API (по два автомобиля каждого из шести рынков), ответы закрытых адресов без сессии и доступные настройки активной ревизии Yandex Containers. Нагрузочные атаки, массовое скачивание фотографий, создание заявок и изменение облачной защиты не выполнялись. Новые платные сервисы не подключались. Любое новое платное решение требует отдельного согласия владельца.

## Фотографии: риск блокировки остаётся

Активный режим `source_urls_only` сохраняет исходные ссылки. В проверенной выдаче всех шести рынков фотографии внешние: Япония — jp2.pa-server.ru; Китай — autoimg.cn; Корея — img.kcar.com и ci.encar.com; ОАЭ — dubicars.com и CloudFront источника; Европа — classistatic.de и autoscout24.net; Грузия — autopapa.ge и static.tnet.ge. Это выборка, а не инвентаризация всех URL.

Браузер посетителя загружает эти изображения непосредственно. Поэтому просмотры не складываются в один исходящий IP нашего контейнера, но источник может ограничить hotlink, домен, отдельные URL, посетителя или прекратить выдачу. Это также может нарушить отображение превью в мессенджерах. Гарантии отсутствия блокировки нет. Условия использования фотографий и срок действия ссылок в этом техническом аудите не подтверждались.

Главное фото загружается при открытии, миниатюры используют lazy loading/низкий приоритет. Повторное использование браузерного кеша зависит от заголовков источника; собственного общего кеша для этих внешних URL нет. В коде существует отдельный режим бинарного сохранения с дедупликацией, лимитами и паузами на 403/429, однако он не включён для активной цепочки — его ограничения нельзя выдавать за защиту текущих просмотров.

Для устранения зависимости нужны разрешённые поставщиком копии/миниатюры в собственном хранилище либо договорённость об устойчивой выдаче изображений. Включать массовое копирование автоматически нельзя: нужны условия источников и согласованный бюджет хранения/трафика. В этом изменении режим хранения не менялся.

## Защита: существующие меры и ограничения

- На проверенном production `/crm` без сессии перенаправляет на вход, `/api/crm/inbox` отвечает 401. Авторизация подписывает cookie HMAC-SHA256; cookie HttpOnly/Secure/SameSite=Lax. Обработчики повторно проверяют сотрудника, актуальную роль, отключение и версию сессии; доступ к заявкам фильтруется по правам.
- Персональные ключи сотрудников генерируются криптографически, хранятся хешами; сравнение ключей constant-time. На логин действует сохранённый лимит 15 попыток за 15 минут на username. Это не глобальный IP-лимит: распределённый поток по разным именам он не остановит.
- В активной ревизии подтверждено наличие секрета авторизации и обеих настроек существующей SmartCaptcha (значения не выгружались в отчёт). Проверка повторных заявок использует подписанный visitor ID и контакты, атомарные счётчики, серверную проверку captcha. Смена идентификаторов/контактов и массовые GET остаются отдельным риском.
- В существующих тестах есть проверки закрытой выдачи заявок, ролей, персональных просмотров, назначений, проверки origin и SSRF/допустимых хостов изображений. Это не полный пентест и не доказательство отсутствия всех уязвимостей.
- По историческому подтверждённому журналу 19.09 SWS отвязан от шлюза по решению владельца. Новый read-only сервисный доступ получает 403 при чтении шлюзов/SWS: актуальную привязку повторно не подтвердил. 403 не означает отсутствие профилей. Права сервисного аккаунта не расширялись. NS домена принадлежат Cloudflare, но A-запись — 158.160.171.31, публичные ответы идут от ycalb без cf-ray. Наличие Cloudflare DNS само по себе не подтверждает проксирование, WAF или DDoS-фильтрацию.
- Активный контейнер: 1 CPU, 2 GiB, concurrency 4, timeout 30 s, одна минимально выделенная копия. Эти настройки не являются DDoS-фильтром или лимитом счёта. Явный предел максимального масштабирования в ответе API не получен; квоты аккаунта и биллинг отдельно не проверялись.

Вывод: базовая защита доступа и повторных заявок присутствует. Подтверждённой комплексной защиты от DDoS и гарантии ограничения расходов нет. После отключения прежней привязки платного ARL нельзя рассчитывать на её лимит запросов. Даже успешное обновление зависимостей не устраняет сетевой/распределённый DoS.

## Исправления безопасности в этой работе

Аудит зависимостей обнаружил устаревший Next.js 14.2.5 с опубликованными advisory, включая обход middleware. Наличие повторных проверок прав в API снижает зависимость от middleware, но не оправдывает старую версию. Опубликовано обновление Next.js до 15.5.24, Sharp до 0.35.4, PostCSS до 8.5.28 и NanoID до 3.3.19. Для встроенного PostCSS Next задан override совместимой ветки 8.x. Docker переведён с Node 20 на Node 22, установка — по lockfile через npm ci. Cookies и динамические параметры маршрутов переведены на асинхронный API Next 15.

`npm audit --omit=dev` после обновления: 0 известных предупреждений на момент проверки. Это результат базы advisory, а не гарантия безопасности приложения. Production middleware теперь отказывает при отсутствии секрета вместо применения публичного dev fallback. Добавлены nosniff и ограничение referrer; CRM и вход защищены от встраивания во фрейм. Публичный партнёрский лендинг не получил запрет встраивания.

Первичный источник по middleware: https://github.com/vercel/next.js/security/advisories/GHSA-f82v-jwr5-mffw . Руководство перехода: https://nextjs.org/docs/app/guides/upgrading/version-15 .

## Интерфейс

Закреплённая компактная шапка; кабинет сотрудника с профилем, звуком и выходом вместо повторяющихся ссылок. На телефоне навигация плитками, показатели по два в ряд, компактные карточки/фильтры заявок и сотрудников. Пояснения ролей, создание клиента и контрольный расчёт раскрываются по запросу. Шесть раскрываемых рынков сохранены. Select на публичных страницах и в CRM получают стрелку с правым отступом 16 px и место под неё.
