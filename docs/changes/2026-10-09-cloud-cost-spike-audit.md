В истории реального avtocena-web ревизия bbak71v189sauhm8jsn4 от 07.10 15:23 (время консоли) имеет 1 vCPU / 2 ГБ, а следующая bbapc5se74goq7phsnbq от 15:35 — 2 vCPU / 4 ГБ. Docker image SHA одинаковый: 07221f178b5187331aa0cf584b417116f6abc05023e55074412e49db834d8b16. Concurrency 4 и один подготовленный экземпляр не изменились. Автор изменения не установлен.

Commit 42120621abe1d776617f9d12e726106e7ac4d3c6 закрепил 2 vCPU / 4 ГБ в deploy-yandex.yml, чтобы последующий deploy не отменял уже установленную конфигурацию. Следующие ревизии 08.10 имеют эти параметры.

При одинаковом оплачиваемом времени увеличение выделенных CPU/RAM удваивает их стоимость; фактическую экономию обратного изменения нельзя считать автоматически 50%: длительность и потребность в памяти тоже меняются. 08.10 соответствует примерно 79,2 суммарным часам активности экземпляров с 2 vCPU, против 47 часов при 1 vCPU 05.10. Значит, кроме удвоения ресурсов выросло и суммарное оплачиваемое время экземпляров. Это не средняя задержка одного запроса: параллельные запросы могут делить один экземпляр.

## Наблюдения и границы вывода

Мониторинг последнего дня открылся; видны многосекундные задержки и ошибки. В текущих REPORT (09.10 04:30 UTC+3) есть запросы длительностью 12,8–23 секунды. Один из запросов 12,823 секунды имеет Billed Duration 11 секунд; текущие отчёты также показывают Max Memory Used до 2152 МБ. Это точечная выборка 09.10, а не измерение распределения за 08.10 и не основание немедленно уменьшать память до 2 ГБ.

Исторический поиск прикладных логов за 08.10 через Cloud Logging после ожидания и одного reload завершился видимой internal error («Произошла непредвиденная ошибка»). Текущие логи и мониторинг доступны; блокировка относится к этой исторической выборке. Не установлены доли конкретных маршрутов, cache miss, Object Storage ожиданий, ботов, cold start, тестовых прогонов и CPU-работы. Нет доказательства, что весь рост вызван аварией Яндекса или Che168.

Recovery Che168 выполняется на GitHub-hosted ubuntu-latest, а не в avtocena-web. Он обращается к Object Storage, но его ожидание API нельзя считать временем выполнения web-контейнера Яндекса. Полная атрибуция исходящего трафика runner требует отдельной проверки.

## Следующие действия

1. Получить ограниченную по времени выборку долгих запросов с маршрутом, длительностью, кодом ответа и расходом Object Storage; сравнить одинаковые окна 05/08.10. При недостаточном логировании добавить безопасные агрегированные замеры без cookies, токенов и query-параметров пользователей.
2. Найти повторное чтение больших файлов, отсутствие совместного кеша/объединения одновременных чтений и дорогую сборку публичных страниц. Исправлять подтверждённый путь, затем сравнить оплачиваемое время, задержки и ошибки.
3. Отдельно атрибутировать 695 ГБ исходящего Object Storage 06.10 по получателям/ключам. Не объявлять весь объём фотографиями или работой фида без журналов.
4. Решение о возврате CPU/RAM принимать после проверки пиков памяти и времени; уменьшение CPU может удлинить ответы, память 2 ГБ уже меньше отдельных наблюдённых значений.
5. Сопоставить следующие полные дни биллинга. Снижение расходов пока не выполнено и не подтверждено.
