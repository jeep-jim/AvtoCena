# АвтоЦена — постоянный roadmap и техническое задание

> Последнее обновление: 2026-07-28
> Статус: обязательный источник контекста перед любыми изменениями проекта.

## 0. Обязательный рабочий протокол

Перед изменением каталога, парсеров, расчётов, CRM, API, JSON-хранилища, GitHub Actions или деплоя необходимо:

1. Прочитать этот файл целиком или соответствующий раздел.
2. Проверить, не ломает ли изменение уже готовый дизайн, SEO-маршруты, CRM, расчётный движок и JSON-архитектуру.
3. Не откатывать весь проект ради восстановления одного слоя. Сравнивать с последней рабочей версией и возвращать только нужную логику.
4. После падения workflow зафиксировать run, commit, этап, симптом и причину.
5. Исправлять минимально необходимый существующий файл.
6. Добавлять или обновлять тест, который воспроизводит проблему.
7. Создавать PR, ждать полного зелёного CI и только затем вливать в `main`.
8. Не считать каталог исправленным только по зелёному CI или зелёному deploy.
9. Для каталога обязательно проверить новый `generationId`, `catalog/manifest.json`, `/api/catalog/market-counts`, реальные карточки, цены и фото.
10. Не заявлять, что источник даёт 1 000 машин, пока это не подтверждено свежим probe/rebuild/publish-отчётом.
11. После значимого изменения обновлять этот roadmap.

Если код и roadmap расходятся, источником истины являются актуальный код, тесты и фактические production-данные. После проверки roadmap необходимо немедленно актуализировать.

## 1. Цель продукта

**АвтоЦена** — сайт, PWA, Telegram-бот и mini app для подбора и расчёта автомобиля «под ключ» примерно за 30 секунд.

Основная ценность:

- большой реальный каталог по семи рынкам;
- реальная цена автомобиля в стране покупки;
- валюта и актуальный курс;
- таможенные платежи РФ;
- утилизационный сбор;
- логистика, брокер, СВХ, лаборатория, СБКТС, ЭПТС и доставка;
- итоговая цена «под ключ» по выбранному городу;
- собственная база знаний моделей, поколений, двигателей и мощности;
- CRM компаний и партнёрская CPA-система.

Основной домен: `avtocena.com`.

Production: Yandex Cloud.

DNS/CDN: Cloudflare + REG.RU.

Репозиторий: `jeep-jim/AvtoCena`.

## 2. Непереговорные архитектурные решения

### 2.1. Только JSON

Единственное хранилище данных проекта — JSON.

Не использовать PostgreSQL, MySQL, MongoDB, Firebase или другую БД без отдельного решения владельца проекта.

JSON используется для:

- каталога автомобилей;
- manifest и индексов;
- базы знаний моделей;
- курсов валют;
- таможенных правил;
- утилизационного сбора;
- логистики;
- SEO;
- CRM;
- лидов;
- компаний и менеджеров;
- партнёров и CPA;
- шаблонов договоров и служебных настроек.

### 2.2. Чанки

- Обычные бизнес-JSON делить на чанки при приближении к 500 записям.
- Production-каталог использует чанки примерно по 250 карточек.
- Не создавать один огромный JSON с тысячами объектов.

### 2.3. Существующие файлы прежде новых

Сначала изменять подходящий существующий файл. Новый файл создавать только при архитектурной необходимости.

### 2.4. Реальные данные

Запрещено публиковать выдуманные объявления, цены, пробеги, характеристики, мощности и фотографии.

Сайт и CRM читают одну опубликованную generation. Демо-CRM не должна показывать вручную придуманные количества машин.

### 2.5. Дизайн и SEO нельзя ломать исправлением парсеров

Без отдельного запроса владельца нельзя менять утверждённый дизайн.

Обязательный путь:

`логотип бренда → /cars/brand/{slug} → список моделей → /cars/brand/{slug}/model/{modelSlug}`

Брендовые и модельные страницы, metadata, canonical, breadcrumbs и sitemap являются частью продукта.

Стабильные ID:

### Целевой объём

- квота до 1 000 проверенных карточек с продуктивного источника за проход;
- минимум 3 независимых продуктивных источника на рынок;
- целевой bootstrap — 3 000 машин на рынок;
- бизнес-цель — минимум 10 000 реальных карточек суммарно;
- верхний публичный лимит — 30 000 машин на рынок;
- retention — 3 дня;
- автоматический проход — один раз в сутки;
- временная блокировка сайта не удаляет уже проверенные карточки.

1 000 — квота, а не обещание. Публикуется только фактически полученное и проверенное количество.

### Бизнес-приоритет наполнения

Сначала формируется массовый сегмент:

1. итоговая рассчитанная цена до 6 000 000 ₽;
2. мощность до 160 л.с.;
3. возраст не более 6 лет;
4. реальные объявления с готовым расчётом;
5. полноценные галереи;
6. после наполнения основного сегмента добавляются дорогие, старые и мощные машины.

Дорогие автомобили не запрещены, но не должны вытеснять доступные предложения из первых тысяч карточек.

## 4. Реестр площадок

Статус источника подтверждается probe/rebuild-отчётом. Наличие адаптера в коде не означает, что площадка доступна с GitHub runner.

Статусы:

- `registered` — адаптер зарегистрирован;
- `probe-live` — probe получил и нормализовал карточки;
- `productive` — источник дал опубликованные машины;
- `blocked` — CAPTCHA, 403, Cloudflare или региональное ограничение;
- `broken-route` — изменился URL, HTML или API;
- `retention-only` — новые данные временно не получены, старые карточки сохраняются.

## 5. Production workflow каталога

Основной workflow:

`.github/workflows/catalog-production-recovery-v15.yml`

Имя: `Catalog source-scale daily`.

Схема:

1. `validate` — синтаксис, тесты и TypeScript.
2. `knowledge` — синхронизация базы знаний в JSON Object Storage.
3. `collect` — 7 рынков × 3 шарда = 21 job.
4. `publish` — объединение артефактов, аудит, расчёт, публикация manifest и smoke.

Ключевые параметры после PR #139:

- Node.js 24;
- `max-parallel: 21`;
- `CATALOG_REBUILD_SHARD_COUNT=3`;
- `CATALOG_REBUILD_TARGET_PER_SOURCE=1000`;
- `CATALOG_REBUILD_TARGET_PER_MARKET=3000`;
- `CATALOG_PUBLISH_TARGET_PER_MARKET=3000`;
- retention `259200000` мс = 3 дня;
- минимум 1 реальное фото для аварийной публикации;
- предпочтительно 8 фото;
- максимум 30 фото;
- `CATALOG_COLLECTION_IMAGE_LIMIT=30`;
- `CATALOG_GALLERY_FAST_PATH=false`;
- `CATALOG_REBUILD_DETAIL_LIMIT_PER_SOURCE=100`;
- image concurrency = 6;
- prepare concurrency = 16;
- сетевой лимит сборщика = 3 300 000 мс;
- timeout collect job = 90 минут;
- артефакты сжимаются и хранятся 1 день;
- cron: `17 20 * * *` UTC;
- concurrency group: `catalog-source-scale-daily`;
- новый run отменяет только действительно устаревший предыдущий run.

Пустой рынок не отменяет публикацию остальных рынков. Предыдущая проверенная версия сохраняется в пределах retention.

Внешний smoke является диагностическим и не откатывает готовый manifest.

Фатальными остаются отсутствие публикации, отсутствие `generationId` и полный ноль карточек.

## 6. Двухэтапное наполнение и галереи

Нельзя пытаться открыть detail и скачать до 30 фотографий для всех потенциальных 21 000 машин в одном часовом проходе.

Правильная схема:

### Этап 1 — массовый листинг и расчёт

1. Получить листинг.
2. Извлечь ID, рынок, источник, марку, модель, год, цену, валюту, URL и фотографии листинга.
3. Нормализовать характеристики.
4. Обогатить из собственной базы знаний.
5. Попытаться рассчитать таможню и утиль по данным листинга и knowledge.
6. Сохранить реальную карточку даже при честном статусе `needs_data`.

### Этап 2 — прогрессивный detail enrichment

Detail/API открывается при следующих условиях:

- нет даже минимальной фотографии;
- отсутствуют критические характеристики;
- машина относится к приоритетному массовому сегменту и галерея меньше 8 фото.

На один источник действует отдельный бюджет detail-карточек за проход.

Галереи расширяются ежедневно и накапливаются до 30 фото в пределах трёхдневного retention.

Shard-report обязан показывать:

- `detailLimitPerSource`;
- `detailReservationsBySource`;
- `detailSuccessBySource`;
- `detailDeferredBySource`;
- `imageStats.minimum`;
- `imageStats.maximum`;
- `imageStats.average`;
- `imageStats.preferredShare`.

Одна обложка не должна навсегда блокировать detail enrichment. Одновременно нельзя перегружать один run сотнями тысяч изображений.

## 7. Правила карточки

Минимально необходимы:

- стабильный ID;
- `sourceId` и `sourceOfferId`;
- один из семи рынков;
- марка и модель;
- правдоподобный год;
- реальная цена источника;
- валюта;
- публичная ссылка на исходное объявление;
- минимум одна сохранённая фотография конкретной машины;
- отсутствие признаков коммерческой техники;
- готовый расчёт либо честный статус уточнения.

Нельзя:

- использовать логотип сайта вместо автомобиля;
- привязывать общую картинку листинга к другой карточке;
- показывать явно нереальную цену;
- публиковать физически неправдоподобную мощность;
- выдавать пиковую мощность EV за сертифицированную 30-минутную.

Если `totalRub` ещё нет, карточка показывает реальную `sourcePrice` + `sourceCurrency` и текст «Расчёт под ключ уточняется», а не «Цена по запросу».

Основные файлы:

- `apps/web/lib/catalog/offer-quality.ts`;
- `apps/web/lib/catalog/spec-normalization.ts`;
- `apps/web/lib/catalog/full-gallery-wrapper.ts`;
- `apps/web/lib/catalog/priority-fast-gallery-wrapper.ts`;
- `apps/web/lib/catalog/storage.ts`;
- `apps/web/components/catalog/CatalogCard.tsx`.

- коробку и привод;

## 9. Таможня и утилизационный сбор

Расчёт выполняется кодом, а не текстовой формулой в UI.

Основные пути:

- `packages/engine/src/calculation/**`;
- `apps/web/lib/catalog/customs-pricing.ts`;
- связанные JSON-правила и тесты.

### Таможня

Учитывать:

- физическое или юридическое лицо;
- возраст автомобиля;
- таможенную стоимость или объём двигателя по действующему режиму;
- тип силовой установки;
- курс валюты на дату расчёта;
- таможенный сбор;
- пошлину;
- акциз и НДС, если применимы;
- маршрут оформления и правила ЕАЭС;
- актуальное законодательство.

### Утилизационный сбор

Учитывать:

- статус импортёра;
- личное или коммерческое использование;
- возраст;
- объём ДВС;
- тип автомобиля;
- мощность по действующей шкале;
- для EV/PHEV — применимую сертифицированную мощность;
- льготные коэффициенты и ограничения перепродажи;
- актуальные коэффициенты на дату расчёта.

Если обязательной мощности нет, точный итог не показывать как подтверждённый.

### Цена «под ключ»

Breakdown может включать:

- стоимость автомобиля;
- комиссию;
- брокера;
- СВХ;
- лабораторию;
- СБКТС;
- ЭПТС;
- таможенные платежи;
- утильсбор;
- международную логистику;
- доставку по РФ;
- другие подтверждённые расходы рынка.

Все строки должны храниться в `calculationSnapshot`/breakdown и проверяться тестами.

## 10. Хранилище и публикация

Production использует JSON Object Storage в Yandex Cloud.

Обязательные переменные:

- `JSON_STORAGE_DRIVER=object`;
- `YC_OBJECT_STORAGE_ENDPOINT`;
- `YC_OBJECT_STORAGE_REGION`;
- `YC_OBJECT_STORAGE_BUCKET`;
- `YC_OBJECT_STORAGE_ACCESS_KEY_ID`;
- `YC_OBJECT_STORAGE_SECRET_ACCESS_KEY`;
- `YC_OBJECT_STORAGE_PREFIX`;
- `CATALOG_IMAGE_CDN_URL`.

Ключевые объекты:

- `catalog/manifest.json`;
- `catalog/internal/manifest.json`;
- `catalog/generations/{generationId}/offers/{market}/chunk-XXXX.json`;
- generation indexes;
- source cursors;
- cached images.

Публикация атомарная:

1. записываются chunks и индексы новой generation;
2. затем переключается публичный manifest;
3. при storage failure предыдущий здоровый manifest сохраняется.

Нельзя сначала очищать старый каталог, а потом собирать новый.

## 11. Сайт, CRM и SEO

Единый источник количества машин — опубликованный `catalog/manifest.json`.

API счётчиков: `/api/catalog/market-counts`.

CRM и сайт должны показывать одну generation.

Флаги рынков отображаются детерминированными SVG, а не буквами JP/CN/KR.

Брендовый rail ведёт на существующие SEO-страницы брендов и моделей.

Публичные DTO нельзя повторно проверять валидатором, который требует удалённые приватные поля `operational` и `sourceId`.

## 13. Диагностика падения workflow

Порядок:

1. Зафиксировать run, commit, время и event.
2. Найти первый реальный failed job.
3. Прочитать steps и logs.
4. Скачать artifacts:
   - `catalog-probe-{market}-{shard}.json`;
   - `catalog-rebuild-{market}-{shard}.json`;
   - validation report;
   - publish report.
5. Определить класс проблемы:
   - syntax/typecheck;
   - missing secret;
   - 403/CAPTCHA;
   - broken route;
   - cursor loop;
   - no progress;
   - timeout;
   - image host blocked;
   - gallery invalid;
   - price/currency invalid;
   - calculation failed;
   - knowledge missing;
   - artifact missing/large;
   - manifest/storage conflict;
   - false fatal gate.
6. Обновить roadmap.
7. Исправить минимальный существующий файл.
8. Обновить тест.
9. Прогнать CI.
10. Влить PR.
11. Проверить новый production run и manifest.

Не делать:

- бесконечные trigger-коммиты;
- технические PR только ради запуска;
- считать cancelled run ошибкой парсера без проверки concurrency;
- снижать качество до фейковых карточек;
- делать один внешний сайт фатальным для всего каталога;
- удалять retention при временном сбое;
- заявлять об исправлении до production-проверки.
